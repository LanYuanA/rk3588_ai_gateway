# 2025-06-09 优化总结

## 一、检测框闪烁问题修复

### 问题描述
检测框在视频画面上闪烁，有时显示有时消失。

### 根因分析
`updateFrame()` 写入新帧时会覆盖 grid buffer 的 ROI 区域，擦掉已画的检测框。而 `updateDetectionResults()` 还没来得及画新的检测框，推流线程就读到了"有帧无框"的画面。

时序问题：
```
拉流线程: updateFrame() → 写新帧 → 擦掉旧框
推流线程: 读到 "有帧无框" → 闪烁
推理线程: updateDetectionResults() → 画新框 (但已经晚了)
```

### 优化方案
**文件**: `src/realtime_composer.cpp`

`updateFrame()` 写入新帧后，立刻重画该路的最新检测结果，保证 grid buffer 里永远是"帧+框"的完整画面：

```cpp
void RealtimeComposer::updateFrame(int stream_id, const cv::Mat& frame) {
    // 先读取该路最新检测结果
    std::vector<DetectResult> latest_dets;
    {
        std::lock_guard<std::mutex> dLock(detection_mutexes_[stream_id]);
        latest_dets = detections_[stream_id];
    }

    std::lock_guard<std::mutex> lock(buffer_mutex_);
    // 写入新帧
    cv::resize(frame, roi_dst, rois_[stream_id].size());
    // 立刻重画检测框
    if (!latest_dets.empty()) {
        drawDetections(roi_dst, stream_id, latest_dets);
    }
}
```

### 锁顺序优化
统一锁顺序为 `detection_mutexes_` → `buffer_mutex_`，避免死锁：
- `updateFrame()`: 先读 detection_mutex，再锁 buffer_mutex
- `updateDetectionResults()`: 先锁 detection_mutex，再锁 buffer_mutex

## 二、推流延迟累积问题修复

### 问题描述
程序运行时，推流画面与实时画面的延迟越来越大。编码耗时在 33ms 以内，但管线中每一步的小延迟累积起来，导致输出流逐渐落后于实时画面。

### 根因分析
推流线程使用固定的 `sleep_until(33ms)` 控制帧率。当编码+推流偶尔超过 33ms 时，下一帧就迟到了，但代码不会跳帧追赶，反而继续处理已过时的帧，延迟越来越大。

### 优化方案
**文件**: `src/streamer_thread.cpp`

1. **绝对时间帧节奏**：用 `next_frame_time += 33ms` 推进帧时间，不用相对耗时计算。处理太慢时自动跳过多个间隔，不累积延迟。

2. **延迟自动重置**：连续 30 帧落后时，重置时间基准（`next_frame_time = now`），彻底清除累积延迟。

3. **漂移监控**：每 300 帧打印一次漂移量（`drift_ms`），方便监控管线是否跟得上实时。

4. **GStreamer 管道加 leaky queue**：在 `appsrc` 和 `h265parse` 之间加 `queue max-size-buffers=3 leaky=downstream`，管道积压时丢弃旧帧保新帧。

### 优化思路
```
旧: 帧1(33ms) → sleep → 帧2(33ms) → sleep → ... (一旦卡顿，延迟永久累积)
新: 帧1(33ms) → 落后?跳过sleep → 帧2(最新帧) → ... (自动追赶实时)
```

## 三、拉流线程错开启动

### 问题描述
4 路 RTSP 流同时连接 mediamtx，导致资源竞争，大量"读取失败，重连"。

### 优化方案
**文件**: `src/puller_thread.cpp`

各路拉流线程启动时错开 1 秒：
```cpp
std::this_thread::sleep_for(std::chrono::milliseconds(streamId * 1000));
```

- 流 0: 立即连接
- 流 1: 延迟 1 秒
- 流 2: 延迟 2 秒
- 流 3: 延迟 3 秒

---

## 四、MPP 解码器支持 H264/H265

### 问题描述
原 `MppH265Decoder` 只支持 H265，不支持 H264。

### 优化方案
**文件**: `include/mpp_decoder.h`, `src/mpp_decoder.cpp`

1. 类名改为 `MppDecoder`（通用解码器）
2. 构造函数加 `MppCodingType` 参数，支持 H264 和 H265
3. 保留 `MppH265Decoder` 别名兼容旧代码

---

## 五、RGA 核心强制绑定 RGA3

### 问题描述
RGA 操作可能被调度到 RGA2 核心，而 RGA2 不支持某些操作。

### 优化方案
检查并修复所有 RGA 调度点，强制使用 RGA3：

| 文件 | 修复内容 |
|------|---------|
| `src/rga_resize.cpp` | `rga_scheduler_mode == 3` 时改用 `RGA3_CORE0 \| RGA3_CORE1` |
| `src/rga_yuv_converter.cpp` | 同上 |
| `src/app_runtime.cpp` | `use_rga2_mode` 强制为 `false` |

---
